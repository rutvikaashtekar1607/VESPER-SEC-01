# SEC-01 V2X Cryptographic Specification

## 1. V2X System Overview

V2X (Vehicle-to-Everything) communication enables vehicles
and surrounding infrastructure or systems to exchange information.

The V2X environment considered in this threat model consists of:

- Vehicle
- Sensors / Electronic Control Unit (ECU)
- V2X communication network
- Receiving vehicle or infrastructure
- V2X telemetry
- Potential attackers

The purpose of this threat model is to identify security threats
to V2X telemetry and classify them using the STRIDE methodology.

---

## 2. V2X Telemetry

Telemetry is information communicated from a vehicle or system
to another system.

Examples of V2X telemetry include:

- Vehicle speed
- Vehicle position
- Direction
- Vehicle status

The telemetry travels through the V2X communication path
from the transmitting vehicle to the receiving system.

## 4. Trust Boundaries

A trust boundary is a point where data moves between systems,
components, or environments with different levels of trust.

For the V2X system, the following trust boundaries are considered:

### TB-01: Vehicle Internal System → V2X Communication

Telemetry generated by the vehicle's sensors or ECU leaves
the vehicle and enters the V2X communication environment.

Potential security concerns include:

- Unauthorized modification of telemetry
- Unauthorized injection of messages
- Impersonation of a legitimate vehicle

### TB-02: V2X Communication → Receiving System

Telemetry travels from the V2X communication environment
to the receiving vehicle or infrastructure.

Potential security concerns include:

- Message tampering
- Information disclosure
- Message disruption
- Fake or unauthorized messages

### TB-03: Attacker → V2X Environment

An attacker may attempt to interact with the V2X communication
environment or its components.

Potential security concerns include:

- Spoofing
- Tampering
- Information disclosure
- Denial of Service
- Unauthorized access

---

## 5. STRIDE Threat Analysis

The V2X system is analyzed using the six STRIDE threat
categories: Spoofing, Tampering, Repudiation, Information
Disclosure, Denial of Service, and Elevation of Privilege.

### 5.1 Spoofing (S)

Spoofing occurs when an attacker pretends to be a legitimate
vehicle, device, or system.

#### V2X Threat

An attacker may impersonate a legitimate vehicle or V2X device
and transmit messages as if they originated from a trusted source.

#### Affected Area

- Vehicle identity
- V2X communication
- Message source

#### Threat ID

`V2X-S-01`

---

### 5.2 Tampering (T)

Tampering occurs when data is modified without authorization.

#### V2X Threat

An attacker may modify V2X telemetry while it is being
communicated between the transmitting vehicle and receiving system.

For example, telemetry such as vehicle speed or position could
be changed before reaching the receiving system.

#### Affected Area

- V2X telemetry
- Communication path
- Received data

#### Threat ID

`V2X-T-01`

---

### 5.3 Repudiation (R)

Repudiation occurs when a sender denies having performed an
action or transmitted a message.

#### V2X Threat

A sender may deny having transmitted a particular V2X message
or performed a specific action.

#### Affected Area

- Message accountability
- Event records
- Sender identification

#### Threat ID

`V2X-R-01`

---

### 5.4 Information Disclosure (I)

Information Disclosure occurs when information is accessed by
an unauthorized party.

#### V2X Threat

An unauthorized party may gain access to V2X telemetry while
it is being communicated between systems.

#### Affected Area

- V2X telemetry
- Communication channel
- Vehicle information

#### Threat ID

`V2X-I-01`

---

### 5.5 Denial of Service (D)

Denial of Service occurs when legitimate communication or
services are disrupted or made unavailable.

#### V2X Threat

An attacker may interfere with V2X communication and prevent
legitimate telemetry messages from being delivered.

#### Affected Area

- V2X communication
- Message delivery
- System availability

#### Threat ID

`V2X-D-01`

---

### 5.6 Elevation of Privilege (E)

Elevation of Privilege occurs when an unauthorized entity gains
permissions or access beyond what it is normally allowed to have.

#### V2X Threat

An unauthorized device or user may gain higher-level access to
V2X system functions.

#### Affected Area

- V2X system access
- Device permissions
- Privileged functions

#### Threat ID

`V2X-E-01`

---

## 6. Threat and Vulnerability Table

The following table summarizes the identified STRIDE threats,
their affected areas, and the potential security impact on the
V2X environment.

| Threat ID | STRIDE Category | Threat / Vulnerability | Affected Area | Potential Impact |
|---|---|---|---|---|
| V2X-S-01 | Spoofing | Attacker impersonates a legitimate vehicle or V2X device | Vehicle identity / Message source | False or unauthorized messages may be accepted |
| V2X-T-01 | Tampering | Attacker modifies V2X telemetry during communication | Telemetry / Communication path | Receiving system may process incorrect information |
| V2X-R-01 | Repudiation | Sender denies transmitting a message or performing an action | Message accountability | Difficulty establishing the origin of an action |
| V2X-I-01 | Information Disclosure | Unauthorized party accesses V2X telemetry | Telemetry / Communication channel | Vehicle or system information may be exposed |
| V2X-D-01 | Denial of Service | Attacker disrupts V2X communication | Communication / Availability | Legitimate messages may not be delivered |
| V2X-E-01 | Elevation of Privilege | Unauthorized entity gains higher-level access | System access / Permissions | Unauthorized functions may become accessible |

## 7. Security Requirements

The identified STRIDE threats lead to the following security
requirements for the V2X environment.

### 7.1 Identity and Authentication

V2X devices and message sources should be authenticated so that
unauthorized devices cannot easily impersonate legitimate
vehicles or systems.

**Addresses:** V2X-S-01 — Spoofing

---

### 7.2 Message Integrity

V2X telemetry should have mechanisms that allow the receiving
system to detect unauthorized modification of messages.

**Addresses:** V2X-T-01 — Tampering

---

### 7.3 Accountability and Event Records

The system should maintain sufficient information to establish
the source and occurrence of security-relevant actions or
messages.

**Addresses:** V2X-R-01 — Repudiation

---

### 7.4 Confidentiality

Where telemetry contains information that should not be publicly
accessible, appropriate protection should prevent unauthorized
parties from obtaining that information.

**Addresses:** V2X-I-01 — Information Disclosure

---

### 7.5 Availability and Resilience

The V2X communication environment should be designed to maintain
availability and recover from communication disruption or
malicious interference.

**Addresses:** V2X-D-01 — Denial of Service

---

### 7.6 Access Control

V2X systems should enforce authorization and least-privilege
principles so that devices and users cannot obtain permissions
beyond those required for their functions.

**Addresses:** V2X-E-01 — Elevation of Privilege

## 8. Cryptographic Security Requirements

The V2X security design shall define cryptographic requirements that address the threats identified in the STRIDE analysis.

### 8.1 Confidentiality

V2X telemetry that contains sensitive vehicle or system information shall be protected against unauthorized disclosure.

### 8.2 Integrity

V2X messages shall include appropriate cryptographic protection so that unauthorized modification of telemetry can be detected.

### 8.3 Authentication

The system shall verify that V2X messages originate from an authorized vehicle, device, or infrastructure component.

### 8.4 Key Management

The cryptographic design shall define requirements for secure key generation, storage, distribution, use, and replacement.

### 8.5 Resource Constraints

Cryptographic mechanisms shall be evaluated against the resource constraints identified for the target system, including computation, memory, code size, and energy consumption.

### 8.6 Cryptographic Selection

No final cryptographic primitive shall be selected solely on theoretical security properties. Selection shall be supported by benchmark evidence and comparison against the defined system constraints.

### 8.7 Security Requirement Mapping

| Security Requirement | Related STRIDE Threat | Required Protection |
|---|---|---|
| Confidentiality | Information Disclosure | Encryption |
| Integrity | Tampering | Message authentication and integrity protection |
| Authentication | Spoofing | Cryptographic authentication |
| Accountability | Repudiation | Secure event/message records |
| Availability | Denial of Service | Communication resilience |
| Access Control | Elevation of Privilege | Authorization and key/access controls |

## 9. Cryptographic Benchmark Plan

The cryptographic benchmark will evaluate the computational and resource requirements of the cryptographic mechanisms considered for the V2X security design.

The official task allocation specifies cryptographic benchmarking of AES-GCM versus ECC.

The Week 4 benchmarking report separately defines a benchmark methodology covering Ascon, ChaCha20-Poly1305, ML-KEM/Kyber-512, and SPHINCS+ under Cortex-M4 cycle-accurate emulation.

These two source documents are retained separately in this specification. No benchmark result or final primitive selection is claimed until the required measurements and validation are completed.

### 9.1 Benchmark Environment

The benchmark methodology uses a Cortex-M4-class target environment and cycle-accurate emulation.

The benchmark environment shall record:

- Processor cycles
- Cycles per byte
- Peak RAM usage
- Code size
- Estimated energy consumption
- Functional correctness
- Feasibility against the defined resource limits

### 9.2 Benchmark Procedure

1. Compile the selected cryptographic implementation for the target architecture.
2. Verify functional correctness.
3. Execute the implementation in the defined emulation environment.
4. Measure cryptographic execution cycles.
5. Calculate cycles per byte where applicable.
6. Measure peak RAM usage.
7. Measure compiled code size.
8. Estimate energy consumption.
9. Compare measurements against the defined resource constraints.
10. Record the results in a comparative benchmark table.

### 9.3 AES-GCM and ECC Comparison Scope

The assigned SEC-01 task requires comparison of AES-GCM and ECC. Because ECC represents a family of algorithms and configurations rather than a single primitive, specific operations must be explicitly defined for benchmarking:
- **ECDH (Elliptic Curve Diffie-Hellman):** Key agreement and session establishment.
- **ECDSA (Elliptic Curve Digital Signature Algorithm):** Message authentication and signing.

The comparison shall evaluate:
- Computational cost (measured in execution cycles converted to execution time under the target allocation)
- Memory requirements (RAM footprint)
- Code size (ROM footprint)
- Energy implications
- Authentication and confidentiality roles
- Suitability for constrained V2X communication
- Implementation feasibility

## 10. Benchmark Metrics

The following metrics shall be collected during cryptographic benchmarking.

| Metric | Description |
|---|---|
| Execution Cycles | Number of processor cycles required by the cryptographic operation |
| Cycles per Byte | Execution cost normalized by processed data size |
| Peak RAM | Maximum RAM required during execution |
| Code Size | Size of the compiled cryptographic implementation |
| Energy Estimate | Estimated energy required for execution |
| Functional Correctness | Verification that the implementation produces the expected cryptographic result |

### 10.1 Cycles per Byte

Cycles per byte shall be calculated as:

Cycles per Byte = Total Execution Cycles / Number of Processed Bytes

### 10.2 Peak RAM

Peak RAM shall represent the maximum memory required during execution, including relevant runtime and cryptographic working memory.

### 10.3 Code Size

Code size shall be measured from the compiled implementation using the target toolchain.

### 10.4 Energy Estimation

Energy consumption shall be estimated from the measured execution cost and the defined target-system assumptions.

### 10.5 Benchmark Evidence

Each reported benchmark value shall identify:

- Cryptographic primitive
- Operation measured
- Target architecture
- Execution environment
- Input or message size
- Measurement method
- Result
- Validation status

## 11. Acceptance / Feasibility Criteria

Cryptographic mechanisms shall be evaluated against the resource constraints defined for the target system, converting measured processor cycles into execution time relative to the workload message rate.

### 11.1 Feasibility Classification

A cryptographic mechanism shall be classified as:

**FEASIBLE**  
When the measured execution time, peak RAM, code size, and estimated energy satisfy the applicable resource constraints and message rate requirements.

**MARGINAL**

When the implementation is within 25% of a single applicable resource limit while remaining within the defined evaluation conditions.

**NOT FEASIBLE**

When the implementation exceeds the applicable resource constraints beyond the defined marginal range.

### 11.2 Resource Evaluation

The feasibility assessment shall consider:

- Execution time and required compute rate
- Peak RAM usage
- Code size
- Estimated energy consumption
- Required workload/message rate
- Cryptographic cycle-accuracy validation status

A feasibility classification shall not be treated as final when the underlying cryptographic cycle measurements have not yet been validated.

### 11.3 Benchmark Acceptance

The benchmark activity shall be considered complete when:

1. The required cryptographic implementations have been successfully compiled.
2. Functional correctness has been verified.
3. Required execution measurements have been collected.
4. Peak RAM and code size have been measured.
5. Energy estimation has been completed where applicable.
6. Results have been compared against the defined resource constraints.
7. Any cycle-accuracy limitation has been documented.
8. No unvalidated measurement is presented as a confirmed benchmark result.
9. The workload/message-rate assumption used for execution-time evaluation has been documented.
10. The final feasibility classification is supported by validated benchmark evidence.

## 12. Current Status and Verification Gaps

### 12.1 Completed
The current SEC-01 work has established:

- V2X system overview
- V2X telemetry definition
- V2X data-flow model
- Trust boundaries
- STRIDE threat categories
- STRIDE vulnerability vectors
- Initial security requirements
- Cryptographic security requirements
- Cryptographic benchmark methodology
- Benchmark metrics
- Initial feasibility criteria

### 12.2 Current Verification Status
The Week 4 report confirms that the development toolchain and Renode-based execution environment have been verified.

A 1,000-instruction NOP test produced a measured result of 1,003 cycles, corresponding to a 0.3% discrepancy.

This validates basic instruction execution in the emulation environment but does not by itself validate cryptographic cycle measurements.

### 12.3 Outstanding Verification Gap
Crypto-specific cycle-accuracy validation remains outstanding.

The planned validation requires:

- Enabling the Cortex-M4 DWT cycle counter.
- Running a reference Kyber-512 implementation matching the configuration used by Heinz [8].
- Comparing the measured DWT cycle count against the published Cortex-M4 reference.
- If the discrepancy exceeds 10%, retuning the Renode configuration or falling back to QEMU as defined in the Week 4 methodology.

Until this validation is completed:

- Cryptographic cycle counts shall not be treated as validated.
- Final cryptographic performance claims shall not be made.
- Feasibility classifications based on unvalidated cryptographic cycle measurements shall remain provisional.
